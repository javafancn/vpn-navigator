# 0.8.14 / Build 34：本机反馈修复

本机确认原安装版本是 0.8.13 / Build 33、本地测试通道。以下改动在源码工作区，尚未替换本机已安装应用。本记录不表示五项真实网络问题已经全部验收。

## 1、2：断开及规则 → 全局切换慢

已确认的代码瓶颈：每条直连路由删除前都启动一次 `/sbin/route get` 核验所有权。添加和删除虽然已有原生路由写入，核验仍导致数千次进程启动。

- 增加独立、复用的只读 `RTM_GET` 套接字，查询序号和进程身份必须匹配，单次查询总期限 1 秒。
- 原生响应转换为现有的严格所有权检查输入，逐条核对目标、掩码和网关/接口；IPv6 处理缩短的掩码和 link-local scope。
- 查询失败保留恢复证据；不通过猜测网关删除路由。引擎退出后才开始断开清理，逐条写前/提交日志和同步落盘顺序保持不变。
- 隔离安装矩阵增加原生读取与系统工具的一致性检查、IPv6 删除后表项不存在检查，以及删除耗时记录。

本机未添加或删除系统路由，没有测得真实 VPN 断开/切换的改善秒数。原生查询已只读核对实际默认路由；完整增删与实际耗时须在隔离安装矩阵和实际 VPN 上确认。

## 3：全局 → 规则后百度仍显示境外 IP

用户确认没有其他代理。代码现在按模式区分 DNS 转发器，切换后先发布新转发器的私有端口，再停旧转发器。发布后除 `dscacheutil -flushcache` 外，再向系统的固定 `mDNSResponder` launchd job 发送 HUP，清理系统解析缓存。断开恢复 DNS 后也刷新缓存。

尚不能确认此前百度现象的唯一根因。浏览器自己的 DNS 缓存、HTTP/2/QUIC 连接及页面结果缓存不由应用直接清除；浏览器缓存的境外站点/CDN 地址也不一定属于中国直连 IP 规则。因此不能把系统 DNS 缓存刷新当作“任意既有浏览器连接立即换出口”的保证。

复测时先等助手核验规则模式完成，再完全关闭浏览器进程后重新打开 IP 查询页面，同时用应用的实际路由解释及公网出口检测核验。若仍异常，记录目标 A/AAAA 地址与实际接口，区分规则覆盖、IPv6 与站点 IP 展示问题。不要仅使用旧标签页的结果作为通过或失败证据。

## 4：全局模式访问国内网站慢

旧代码仅在规则模式使用具有快速备用解析器切换的 DNS 转发器；全局模式将多个 VPN DNS 直接交给系统。首选 DNS 失联时可能出现较长解析等待。

全局模式现在复用同组解析器 250 ms 后备查询逻辑，但显式丢弃全部国内直连解析器。无论查询国内还是国外域名，都只使用 VPN DNS，企业补充 DNS 与原有解析器路由保留。未把国内网站绕过全局 VPN。

回环测试证明全局模式 UDP/TCP 在首选解析器失联时能使用同组备用解析器，且国内服务器没有收到请求。它不代表真实国内网站访问速度：境外出口绕行、线路拥塞及 CDN 定位仍须用同一服务器下的 Original/全局/规则测量来判断。

## 5：开机助手阻止安装/卸载

- 新助手配置 `RunAtLoad=false`，保留 MachServices 按需启动；维护校验仍接受旧版 `RunAtLoad=true` 的精确配置。
- 安装包不再仅因助手在运行而拒绝。先检查主程序/规则任务已退出、没有会话及网络恢复证据，再停止固定本地 launchd job，确认进程消失，并再次检查恢复记录后才发布安装事务。
- 卸载包采用相同空闲助手检查，支持安装批准仍有效时的卸载。安装工具先验证现有程序身份，降权至批准记录中的用户，由该用户移除自己的登录/规则 LaunchAgents，然后退役批准并删除系统组件。
- 活动会话、未恢复的路由/DNS/PF、异常进程或不完整安装仍拒绝覆盖。不会向未知 PID 发送强制结束信号，不删除恢复证据。
- 使用与安装版本配套的可信卸载包；旧版已经下载的卸载包本身不会自动获得这些修复。应用仍在运行时需先退出；活动 VPN 仍需先断开并恢复。
